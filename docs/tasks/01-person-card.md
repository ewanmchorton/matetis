# Задание: карточка человека в базе

Открой этот текст в отдельном чате и выполни только его. Архитектура уже принята в `docs/architecture.md`. Макеты интерфейса ещё не готовы: экраны приложения не меняй.

## Зачем это сейчас

Supabase сам хранит почту и пароль. Имени, согласия на обработку данных и признака «администратор» у этой записи нет. Пока для них нет отдельной таблицы, регистрацию в приложении делать рано: имя и согласие будет некуда записать, а все следующие таблицы (практики, прогресс, друзья) должны ссылаться на человека.

Экран входа из прототипа не трогаем. Его внешний вид ещё изменит дизайнер.

## Результат

В проекте Supabase во Франкфурте (`eu-central-1`) появляется таблица `public.profiles`. При создании записи входа Supabase сам создаёт ровно одну такую карточку. Человек через обычный ключ приложения видит и меняет только свою карточку и не может назначить себя администратором.

В репозитории лежит SQL-файл, по которому эту таблицу можно создать заново. Секреты в Git не попадают.

## Что создать

Таблица `public.profiles`:

| Поле | Смысл |
|---|---|
| `id` | Тот же идентификатор, что у записи входа `auth.users`. При удалении входа карточка удаляется вместе с ней |
| `display_name` | Имя, которое человек вводит при регистрации. Пустым не бывает |
| `role` | `user` или `admin`. У новой карточки всегда `user` |
| `personal_data_consent_at` | Момент, когда человек согласился на обработку персональных данных |
| `created_at` | Когда карточка создана |
| `updated_at` | Когда карточку последний раз изменили |

Почту и пароль в эту таблицу не копировать. Они остаются в записи входа.

Дату рождения, тип человека, друзей и прогресс в эту таблицу не добавлять. Для регистрации они не нужны.

Правила доступа:

- Таблица закрыта правилами PostgreSQL (row level security).
- Читать можно только свою строку.
- Менять можно только своё имя и время изменения. Поле `role` через ключ приложения не меняется.
- Вставлять и удалять строки ключом приложения нельзя. Строку создаёт только база в момент появления записи входа.

Если имя при создании входа не передали, для проверки из кабинета Supabase подставь часть почты до знака `@`. Время согласия в этом проверочном случае — время создания записи.

## Что проверить

1. В проекте выбран регион Франкфурт.
2. SQL из репозитория применён к этой базе.
3. Две проверочные записи входа дают две карточки, не одну и не ноль.
4. Запрос с ключом одного человека не возвращает карточку другого.
5. Запрос с ключом человека не может сменить `role` на `admin`.
6. В Git нет файла с паролями и секретными ключами. Публичный адрес проекта и публичный ключ можно описать в примере настроек без секретов.

## Не делать в этом задании

- Не менять экраны прототипа.
- Не подключать свою почту для писем.
- Не создавать хранилище книг.
- Не выкладывать сайт на Cloudflare.
- Не добавлять таблицы практик, прогресса и друзей.
